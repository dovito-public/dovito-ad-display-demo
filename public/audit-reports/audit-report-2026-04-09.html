Section 01

Executive Summary

▶

Context, purpose, and headline findings for the public demo audit.

The subject of this audit is dovito-ad-display-demo — a public, frontend-only fork of the Dovito Ad Display production codebase. Every server-side component (Postgres, NextAuth, Stripe, Supabase, Mailgun) has been surgically removed and replaced with an in-browser mock layer that intercepts window.fetch and persists state to localStorage. The demo exists to let prospects click through every screen of the product without requiring a real deployment. It is intentionally not a production system, and this audit evaluates it on those terms.

The codebase earns an overall grade of C. The frontend architecture is clean and idiomatic — modern Next.js 16 App Router, React 19, Tailwind 4, shadcn/ui, and React Query, all held together by a small (~1,100 LOC) mock layer that is genuinely well factored. TypeScript strict mode is enabled and there are zero any usages in the application source. Where the grade sags is in areas that simply cannot be fulfilled by a static demo: there are no tests, no error handling on mock API failure paths (because mock calls do not fail), no backend to secure, no monitoring, and no multi-tenant substrate. An honest assessment must score those categories near zero.

The three most notable strengths are: (1) a clean mock-layer abstraction — mock-fetch.ts patches window.fetch once, routes /api/* calls to a pure function in mock-api.ts, and all state mutations flow through a tiny mock-store.ts backed by localStorage; (2) strict TypeScript with zero escape hatches in application code; and (3) full surface coverage — 19 page routes and roughly 50 mocked endpoints faithfully reproduce the real product's user journeys, including the admin dashboard, the advertiser application flow, and the ad display kiosk.

The three most significant concerns — each of which would be critical on a real deployment and is acknowledged as intentional on the demo — are: (1) no auth enforcement whatsoever; anyone navigating to /admin is granted admin access and can observe all mocked data; (2) mock credentials are readable client-side by design; and (3) source maps and next.config.ts-disabled image optimization are shipped in production, which are real findings against the GitHub Pages deployment. On the SaaS-readiness dimension, the demo scores ~10% — not a failure, but a structural consequence of having no backend at all.

The replacement value of the frontend work, assessed conservatively, lands between $60K and $180K depending on team structure. Productising the demo into a real multi-tenant SaaS would require a further $150K–$300K of backend, auth, billing, and platform work on top.

Why publish this? Our paid audits produce a client-facing report that the client rarely shares. This case study is identical in structure, scope, and methodology — the only difference is that the subject is a repository anyone can clone. When we tell a prospect "we'll deliver a report like this," this is the document we point to.

Key Findings

Strength

Clean mock-layer abstraction

The mock-fetch.ts / mock-api.ts / mock-store.ts triad totals ~1,100 LOC and implements a faithful, testable simulation of a REST backend. window.fetch is patched exactly once, /api/* is routed to a pure function, and every mutation flows through a single insertOne/updateOne/deleteOne set of helpers.

Strength

Zero any in application source

An exhaustive grep of src/ finds no any type annotations in application code. Four explicit any usages exist inside the mock layer itself where they are structurally justified (generic collection store, fetch interceptor body), each with an eslint-disable comment.

Strength

Strict TypeScript enabled

tsconfig.json has "strict": true with no escape flags. Combined with the absence of any, the type system is doing real work.

Critical

Zero test coverage

No test files, no test runner, no CI gate. This inherits from the production codebase — which has the same gap — but on a demo repo the absence is felt less acutely because there is nothing to break beyond the UI.

High

No failure paths in mock API

The mock router in mock-api.ts never returns an error — its fallback is a cheerful { success: true, demo: true }. Code downstream of a React Query call therefore never exercises its error branch. This is a verifiable runtime bug for any consumer that reads error states, and it would become a real production bug if the mock layer were replaced with a real backend.

Medium

localStorage reads on every store access

mock-store.ts calls load() on every public helper, performing a synchronous JSON.parse of the entire store per operation. For a demo with a few hundred records this is invisible, but it is a pattern worth flagging because it will not scale if the store is reused elsewhere.

Medium

No error boundaries

The app has no React error boundary components. An uncaught render error anywhere below the root layout will blank the entire page.

Info

Consistent component conventions

39 components under src/components/, all using the same React Query + shadcn/ui + Tailwind idioms. Naming is consistent (kebab-case files, PascalCase exports). ESLint + Next ESLint config present.

Info

README is genuinely useful

The repo README accurately describes the demo's provenance, the mock layer, and what was stripped out. Inline comments are sparse but the code is readable enough that this is not a red flag.

High Severity Findings

High – SEC-001

Source maps shipped to production

next.config.ts does not disable source map generation for the static export, and at least one .js.map file is present under out/_next/static/chunks/ in the deployed bundle. On a static GitHub Pages deployment this means the original TypeScript sources are trivially recoverable. On the demo this leaks nothing sensitive; on any real engagement it would leak the entire client-side codebase to adversaries.

High – SEC-002

No HTTP security headers on GitHub Pages

GitHub Pages does not set Content-Security-Policy, X-Frame-Options, Strict-Transport-Security, Referrer-Policy, or Permissions-Policy. A static-export Next.js app cannot inject headers at runtime. For the demo this is acceptable; for any real deployment the app must be fronted by a CDN or edge worker capable of header injection.

Performance Findings

Frontend

Image optimization disabled

next.config.ts sets images: { unoptimized: true } because static export cannot use the Next image optimizer. Every /demo-images/*.jpg is served at its original size and format. This is a structural constraint of static export on GitHub Pages, not a bug.

Frontend

Bundle: 2.2MB of JS chunks

The out/_next/static/chunks/ directory is 2.2MB uncompressed across ~40 chunks. After gzip this is probably in the 600–800KB range — high but not extreme for a React 19 + framer-motion + radix-ui + React Query stack. No dynamic imports beyond Next.js route splitting.

Runtime

Synchronous localStorage on every mock call

Each call through mock-store.ts does a full JSON.parse of the root store. For ~200 seed records this is microseconds, but it blocks the main thread and will scale poorly if the store grows.

Runtime

No memoization of expensive computations

Spot-checks of the admin dashboard and analytics view show inline .filter().sort() chains in render bodies without useMemo. Not a bug — a finding worth flagging for growth.

Network

Static hosting means trivial CDN caching

GitHub Pages serves every file with an ETag and modest cache headers. First paint after initial load is dominated by Next.js runtime and framer-motion, not network.

Rendering

React Query handles stale-while-revalidate well

Default React Query configuration plus a 150ms artificial delay in the mock layer produces a convincing "real API" feel without blocking interactions.

Info

Font loading via Google Fonts <link>

Fonts are loaded via preconnect + stylesheet, not next/font, because the deviation report audit pages predate the rest of the refactor. Low impact on a demo.

Info

Single artificial latency constant

Every mock call waits DELAY_MS = 150. Flat latency is unrealistic but serves the demo's purpose of showing skeletons and loading states.

Recommendations & Roadmap

▶

A phased roadmap for anyone taking this demo forward — whether as a reference artifact, an internal tool, or the seed of a real product.

Phase 1 – Immediate (days)

Clean up the shipped artifact

These fixes take hours, not weeks, and remove the honest-but-avoidable findings from this audit.

Disable source maps in production build Add rel="noopener" to 2 external links Run npm audit fix for the high + moderate advisories Add a root React error boundary
Phase 2 – Short-term (weeks)

Harden the demo as a reference artifact

If the demo is going to keep earning its keep as a sales artifact, these changes make it more resilient and more useful.

Add Vitest + a smoke test suite for mock routing Simulate error responses in mock layer for at least 5% of calls Memoize expensive admin dashboard computations Front-load the store: single load + in-memory mirror, write-through to localStorage Deploy behind a CDN that injects security headers
Phase 3 – Medium-term (months)

Productisation — if that is the goal

Everything required to convert the demo into an actual SaaS. Detailed breakdown lives in the SaaS Readiness report.

Real backend (Next API routes or separate service) Postgres schema + migrations + ORM (reintroduce Drizzle) NextAuth + role hierarchy + session management Real Stripe integration + webhook verification Tenant scoping in schema and query layer Email transactional layer
Phase 4 – Long-term (quarters)

Platform features

The work that lives beyond "it is a SaaS now" — monitoring, billing ergonomics, admin tooling.

Structured logging + error tracking (Sentry) Per-tenant branding and display customization Usage analytics and billing portal API keys for integrations Self-service onboarding and invitations
